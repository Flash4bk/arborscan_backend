## Состав кандидата и границы

PostgreSQL 17.6, PostgREST 14.17, Storage API 1.79.20/FileBackend и внутренний
nginx закреплены по digest в [ops_selfhost_stack.py](ops_selfhost_stack.py).
API v3/v4 используют точные прежние образы; их env сохранён, кроме локальных
Supabase URL и служебного ключа. Приложение сохраняет собственную авторизацию
ArborScan; GoTrue, Studio и публичный SQL-интерфейс не добавляются.

Вход использует прежние `public.users`/`auth_sessions`, включая хеши паролей,
Google subject и индекс его уникальности. HTTP-клиент приложения обращается
к VPS, а оригиналы/маски текущих отчётов и контуров получает как base64.
Единственное сетевое изображение в действующем Flutter - аватар профиля;
`ApiConfig.imageUrl` сохраняет абсолютные URL. Проверенный набор не содержит
старых облачных Supabase-ссылок, но любые новые внешние ссылки требуют
проверки при появлении, а не безусловной замены пользовательских данных.
Новый интерактивный вход Google в этой операции не проверялся; сохранение
его политики/идентификаторов не выдаётся за новый Google UI-тест.

Внешние Google, PlantNet, OpenWeather, SoilGrids и картографические сервисы
остаются отдельными зависимостями со своими доступностью и лимитами. Их
реквизиты и TLS-проверка сохранены. Перенос собственной БД и Storage снимает
прежнюю зависимость входа/сохранения от облачного REST, но не гарантирует
доступность сторонних сервисов. Новые подписки не подключены.

DB/REST/Storage не имеют host ports. Gateway доступен только на
`127.0.0.1:19080`; при подготовке API использовали `127.0.0.1:19000/19001`,
после переключения работают на прежних loopback-портах 8000/8001. HTTPS,
публичные маршруты и сертификат не менялись. Сохранены точные API images:
v3 `sha256:60c6cf1fc185e41aaf6275522df851b60f142887554685ce7aec49b3f702a990`,
v4 `sha256:034a9d67b49adb5565a1af9454706a104721e21160d725db32a31f796ff20193`.
Сверенный model SHA:
`626f62b97b05fd65275dc3f909c3aec090f6c9957c4ef9f12c4e743a1f75a2bb`.
Модели используются из проверенных
копий с прежними режимами доступа; обучение не запускается. Worker имеет
ручной profile, автоматический старт отключён.

Установленный APK продолжает обращаться к прежним HTTPS-адресам. Для
восстановления входа/анализа после серверного переключения переустановка,
выход из аккаунта или очистка данных приложения не требуются. Текущая задача
не считает новую сборку APK установленной или проверенной на телефоне.

Служебные реквизиты созданы заново с энтропией не менее 256 бит. Срок JWT
задаётся явно, по умолчанию 3650 дней; точная дата содержится в приватном
`rootmanifest.safe.json`. До этой даты нужна согласованная ротация JWT secret,
anon/service JWT и соответствующих env API/REST/Storage. Пароли локальных
служебных ролей PostgreSQL ротируются отдельно. Секреты нельзя выводить
`docker inspect`, копировать в чат или включать в Git. Закрытые конфиги
включаются в приватную резервную копию, поэтому доступ к ней также ограничен.

## Обязательные проверки перед переключением

1. Снять свежие source public/Storage fingerprints через разрешённое прямое
   PostgreSQL-соединение. Сравнить их с независимым source manifest; выводить
   только counts/digests, не записи пользователей. Все запросы read-only.
2. Проверить каждый Storage-файл по SHA256, полные строки metadata/owners/
   versions/timestamps, модели, точные API images и сохранённую Google policy.
3. Отдельными DEMO-записями проверить парольный вход, права владельца,
   версии отчётов, старые PNG, редактор, ревизии, модерацию и повторный запрос.
   Проверить настоящий анализ и повторное открытие после перезапуска.
   Собственные синтетические ревизии затем изолировать от exporter существующим
   `purpose=export_smoke_test_only_not_model_evaluation`: только точный список
   созданных fixtures, с приватной копией и сверкой неизменности фото/маски/
   редактора/решений. Само имя DEMO не исключает accepted revision из обучения.
   Проверить фактический отказ exporter, не создавая датасет и не запуская jobs.
4. Создать полный локальный backup: native DB, физические файлы с xattrs,
   конфигурация и точные runtime images. Реально восстановить его в другой
   новой изолированной среде. Проверка SHA/списка архива не заменяет restore.
5. Только после успешных пунктов 1-4 подготовить и применить promotion.
   Фактические пути backup/restore receipt должны быть записаны в отчёте.

## Выполненная процедура переключения и возобновления

Процедура выполнена точными tools `ROOT/release-tools-682ec13`. Ниже приведён
её порядок для разбора, а не запрос повторно переключать уже работающий сервис.
Свежий source proof обязателен; одного старого audit receipt недостаточно.

```sh
ROOT=/home/arborscan/selfhost-20261012T140855Z
TOOLS="$ROOT/release-tools-682ec13"
python3 "$TOOLS/ops_selfhost_promote.py" prepare --root "$ROOT" \
  --backup /home/arborscan/ops-backups/20261012T183850Z \
  --restore-receipt "$ROOT/backup-restore-checks/20261012T184346Z-bcad9cd5ecc3/result.json" \
  --source-proof "$ROOT/source-pre-cutover-proof-20261012T190140Z.json"
python3 "$TOOLS/ops_selfhost_promote.py" activate --root "$ROOT"
```

`prepare` требует реальные proof-файлы audit, restart, inference, quarantine,
source и restore, сверяя restore с точным backup manifest.
Перед первым остановленным контейнером `activate` сохраняет прежний Compose
и журнал с точными container IDs. Исходные контейнеры останавливаются,
переименовываются и сохраняются; удаления и `reset --hard` нет. Worker не
запускается. Новая БД и файлы не перезаписываются при возобновлении.

После обрыва той же операции допускается повтор `activate` с тем же `ROOT`.
Фазы `parking_originals`, `originals_parked`, `local_api_starting` позволяют
продолжить по фактическим IDs без повторного rename. Источник истины - приватный
`promotion.private.json`, а не отдельный исторический маркер `PROMOTED`.

После успешного старта выполнены оба публичных HTTPS health, отказ без токена
и реальный тестовый цикл входа/анализа/истории.
`health: ok` сам по себе не доказывает работоспособность БД или Storage.

## Откат

После публичных проверок в локальной БД уже есть новые сессии и отчёт.
Локальные БД и Storage теперь являются рабочим источником новых данных;
облачный проект не является автоматически синхронизируемой копией.
Возврат к прежней облачной БД сейчас недопустим: он скрыл бы эти записи.
Следующая команда описывает только прежнее окно до новых записей и не является
командой отката текущего состояния:

```sh
ROOT=/home/arborscan/selfhost-20261012T140855Z
python3 "$ROOT/release-tools-682ec13/ops_selfhost_promote.py" \
  rollback-before-writes --root "$ROOT"
```

Команда применима также при частично завершённом parking и может продолжить
прерванный `rolling_back`. Она паркует локальные API, возвращает сохранённые
исходные контейнеры по IDs, не удаляет тома и не запускает worker. Возврат к
Supabase восстанавливает прежнюю конфигурацию, но не отменяет его HTTP 402.

При новых локальных записях такой откат запрещён: старая облачная БД уже
устарела. Откат приложения должен сохранять новую локальную БД/Storage и
восстанавливать только проверенные API images/config. Обратный перенос данных
требует отдельной согласованной процедуры; автоматически он не выполняется.
Обслуживание рабочих API использует именно новый приватный Compose, сохраняя
локальную БД и Storage. Перезапуск двух API при необходимости:

```sh
ROOT=/home/arborscan/selfhost-20261012T140855Z
docker compose -f "$ROOT/compose.private.json" restart v3 api
```

Изменение image для API-only rollback требует отдельного проверенного образа
и сохранения текущих локальных env/mounts. Простой запуск прежнего rollback
контейнера вернул бы его облачные реквизиты, поэтому его применять нельзя.

Изоляция собственных тестовых контуров выполняется
`python3 "$ROOT/ops_selfhost_quarantine.py" --root "$ROOT"` только до promotion
после успешного restart smoke. Команда повторяема при неизменных fixtures;
посторонний владелец, объект исходного manifest, новая неизвестная запись
или изменение любого поля кроме purpose блокируют процедуру. SQL-решения
модерации она не меняет. Исходные реальные записи не входят в её allowlist.
Новые DEMO-ревизии, созданные после этой процедуры, автоматически не наследуют
purpose marker; перед возможным экспортом их надо отдельно учесть и изолировать.

## Резервное копирование после перехода

[ops_selfhost_backup.py](ops_selfhost_backup.py) читает локальные DB/Storage
без повторного облачного скачивания. Формат включает filesystem metadata,
UID/GID, mode и xattrs; восстановление только логических байтов не заменяет
физическое восстановление FileBackend. Исходные переходные backup защищаются
от ротации. Новая копия публикуется только после проверки; незавершённый набор
не заменяет прежний `COMPLETE`.

Tools для ежедневной службы установлены на новый источник. Первый запуск
19:26:49-20:06:49 UTC завершился по timeout после публикации `20261012T193726Z`.
Сам набор и результат systemd проверяются раздельно. После установленного
исправления 20:45:27-21:05:21 UTC та же операция реально завершилась с exit 0;
возраст COMPLETE остался 19:53:32 UTC. Прежний systemd timer enabled/active,
следующий календарный запуск в момент receipt назначен на 13.10 03:18:48 UTC,
но ещё не наблюдался. На Windows есть COMPLETE обоих новых наборов `183850`
и `193726`; весь pull завершился exit 1 при проверке исходных manifest с CRLF.
Финальный reader e65d836 установлен; полная процедура через настоящий
Scheduler завершилась exit0 в 21:32:55 UTC. Исходные14 защищены, удалений0.
Подтверждены 19 локальных комплектов; последние данные взяты из snapshot
193726Z, его повторная проверка не создаёт новый snapshot.
Фактический SQL/raw restore выше относится к `183850`. Проверка более позднего
`193726` по SHA/native/runtime receipts не выдаётся за новый SQL/raw restore
именно этого набора.
Доступ journal ограничен собственным событием; сообщения системного manager
целиком не прочитаны. Существующая
`D:\ArborScanBackups` остаётся вторым местом; новых дисков/подписок не создаём.
Та же VPS-копия не защищает от потери VPS, а Windows-копия требует доступного
ПК. Независимый отдельный получатель по прежнему общему плану остаётся открытым.
