## Контракт первого сценария

Метод `healthy_circular_section_mor_v1`, версия 1.0.0, реализован независимо
в `arborscan_science/section.py`. Формула для здорового сплошного круглого
сечения: `M = effective_MOR * I / radius`, `I = pi * radius^4 / 4`.
Эквивалентная проверочная запись: `M = pi * effective_MOR * diameter^3 / 32`.
Источник постановки - Hale et al. (2015), DOI 10.1016/j.envsoft.2015.01.016.
Код ForestGALES не переносился.

Входы: диаметр выбранного сечения в метрах и effective MOR в паскалях.
Каждый вход имеет `value`, `unit`, `origin`, `source`. Требуются явные
`section_model=healthy_solid_circular` и `strength_definition`, поясняющий
уже включённые поправки. Поправки повторно не применяются. Нет значения
по умолчанию по породе. Неизвестная неопределённость остаётся неизвестной.

Выход - момент одного заданного сечения, Н·м, с исходными входами, SHA,
методом, ограничениями и `field_validated=false`. Он не является β,
сопротивлением корней, общей устойчивостью дерева, критическим ветром
или вероятностью повреждения. Наличие гнили, полостей, иных сечений и
условий материала нельзя установить этой формулой или одной фотографией.

### API и хранение

| Запрос | Назначение |
|---|---|
| `GET /v4/science/capabilities` | Версия контракта и доступные сценарии, требуется Bearer |
| `POST /v4/science/section-capacity` | `source_version_id`, стабильный `version_id`, `inputs`; требуется Bearer |
| `GET /v4/reports/{version_id}` | Повторное открытие точной версии существующим механизмом истории |

Новый сценарий создаёт дочернюю версию существующего отчёта. Владелец
проверяется сервером. Исходное фото, измерения, исходный отчёт и контуры
не изменяются. `science_result` - отдельное поле верхнего уровня,
создаваемое сервером; обычная загрузка снимка не позволяет его назначить.
Результат привязан к версии, SHA её содержимого, SHA фото и correction_id.
SHA реализации численного метода сохраняется вместе с SHA входов и результата.

Используется существующая транзакция `save_report_version`: одна дочерняя
версия на родителя, сравнение содержимого при повторном version_id.
Одинаковый повтор возвращает прежнюю запись, изменённый пакет либо второй
ребёнок того же родителя даёт 409. Blob без подтверждённой индексной записи
не считается сохранённым. Сетевой таймаут - неопределённый исход; повтор
должен использовать прежние параметры и version_id.

Новая миграция для первого сценария не требуется. Это вывод по использованию
существующего контракта, а не заявление о выполнении SQL на production.
Тестовая файловая модель индекса проверяет повторное чтение после создания
нового сервиса; она не заменяет конкурентный прогон настоящего PostgreSQL.

Старый клиент продолжает читать обычный `report`; новое поле не требует от
него научных расчётов. Новый клиент со старым API должен показывать
недоступность сценария при 404/405 и сохранять работу обычной истории.
Серверный образ v4 обязан содержать обе папки `arborscan_v4` и
`arborscan_science`.

## Интерфейс и долговечность сценария

Из сохранённой серверной версии: «Расчёты: сценарий сечения». Пользователь
вводит диаметр в м/мм, effective MOR в МПа, происхождение и источник обеих
величин, определение прочности/включённых поправок и подтверждает допущения.
На сервер уходят м/Па; прочность из вида дерева или фото не подставляется.
Ожидаемый результат - отдельная карточка сценария с Н·м, входами, методом,
версией и SHA. Он не заменяет обычные размеры и не становится β/CWS.

Черновик raw-формы, pending operation UUID/body и подтверждённый малый
science_result сохраняются в SharedPreferences по owner/source version.
Пересоздание страницы/сервиса и остановка процесса не требуют состояния
редактора в памяти; последние завершённые записи восстанавливаются.
Смена аккаунта скрывает чужие данные и отклоняет его незавершённый ответ.
Выход и повторный вход в тот же аккаунт на том же устройстве не синхронизируют
черновик на другое устройство. Переустановка/очистка данных удаляет локальный
черновик; только подтверждённая серверная версия доступна после входа на
другом телефоне. Без сети можно открыть уже доступные локальные входы/кеш;
новый серверный расчёт не выполняется и не объявляется сохранённым.

При неизвестном исходе поля закреплены и повторяется один запрос. Изменить
их можно только после явного серверного422 через «Исправить входы», создавая
следующий intent UUID; исходная форма сохраняется. При404/405 старого API
функция понятным образом недоступна, обычные отчёты/анализ остаются рабочими.
Один подтверждённый `saved:true` недостаточен: проверяются также persisted,
версия контракта, точный result/source ID и совпадение SI-входов.

## Текущая эксплуатационная диагностика

Первичная read-only проверка VPS установила причину повторных неудач backup:
прежняя конфигурация архивов runtime не содержала текущий образ v4
`sha256:2abb56ed5d84e4ddbe4465da851c842861498101f030fab016f66630c4ee1762`.
Восемь попыток операции 05.11 доходят до проверки runtime, затем прекращаются.
Плановый минимум свободного места - 4 ГиБ. Накопление незавершённых попыток
увеличивает расход диска. `timer active` не означает успешную копию.

Подготовлены и source-bound проверены preflight, immutable index repair,
архивный verifier и ограниченный cleanup/rollback. В существующей
`D:/ArborScanBackups/remediation-20261112T104112Z` реально восстановлен и
проверен runtime tar текущего v4: **608808960 байт**, SHA256
`3e7935ea2eb0d691247698a6873b1c1a6c4b71e5d659d547ecf34aa8bfe25d0b`.
Точный OCI linux/amd64 image и все blob SHA проверены; реальный Docker
load/start этим не выполнен.

До возможной уборки сохранены все **98 файлов /12404171781 логических байт**
семи failed attempts и98 file/21 directory metadata, включая uid/gid/mode/
mtime/xattrs. Quarantine COMPLETE proof SHA256:
`84758463ba8e68debb0ce8d707de9881d48eafcfc5249fe93e134639b096c3c6`.
Tracked reader воспроизвёл исходные raw-file SHA из закреплённых архивов и
