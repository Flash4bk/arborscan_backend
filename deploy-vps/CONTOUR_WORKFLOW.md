# Цикл работы с контурами (не развёрнут)

Проверенный HTTPS-коммит `be8485b963f6579feb559d5fc938959fff320d84` включён
в `main` через fast-forward и отправлен. Новая функциональность находится только
в `codex/contour-workflow`. Описанные ниже команды развёртывания **не выполнялись**.
Существующие контейнеры, private bucket и production DB не изменялись.

## Данные и переходы

Существующий private bucket `arborscan-corrections` и путь
`v4-corrections/{owner_uuid}/{analysis_uuid}_{revision_sha256}.json` сохранены.
Запись schema_version=2 содержит исходные байты фото, итоговую PNG-маску,
`original_ref.image_sha256`, `parent_id`, `editor_state`:

```json
{
  "version": 1,
  "coordinates": "normalized_oriented_image",
  "width": 1080,
  "height": 1920,
  "closed": true,
  "points": [{"x": 0.2, "y": 0.1}, {"x": 0.8, "y": 0.1}, {"x": 0.5, "y": 0.9}]
}
```

Начало координат — левый верхний угол ориентированного фото, x вправо, y вниз.
Ширина и высота — пиксели после применения ориентации изображения. Координаты
нормированы в [0,1]. Восстанавливаются геометрия и замкнутость, а не экранный
масштаб/панорамирование или стек Undo. PNG не используется для извлечения точек.
Незавершённые локальные контуры допускают `closed:false` и меньше трёх точек;
сервер принимает только замкнутый контур, 3–4096 конечных точек, JSON ≤256 KB.
Ограничения фото 15 MiB, маски 8 MiB, разрешения 25 MP сохранены. PNG и фото
должны иметь одинаковые ориентированные размеры; пустая/полная маска запрещена.

Состояния: `draft → submitted → accepted | rejected`. Редактирование создаёт
дочернюю ревизию в `draft`, даже если родитель принят. Решение относится к одной
ревизии и не перезаписывается; повтор того же решения того же администратора
идемпотентен. История содержит отправку и решение с actor_id, временем и причиной.
При отклонении причина обязательна, максимум 2000 символов.

`contour_revisions` — источник текущего статуса, JSON-объект остаётся неизменяемым.
API накладывает актуальную метаинформацию на запись. Новые endpoint'ы:

- `GET /v4/corrections/workflow/capabilities`: готовность миграции, версия 1.
- `POST /v4/corrections/workflow`: multipart `analysis_id,image,mask,editor_state,parent_id?`.
- `POST /v4/corrections/{id}/submit`: явная отправка автором.
- `GET /v4/corrections/workflow/queue?offset=0`: очередь администратора.
- `GET|POST /v4/corrections/workflow/review/{owner}/{id}`: просмотр / решение.
- POST решения: `{"decision":"rejected","reason":"..."}` либо `accepted`.

Все запросы используют существующий Bearer-токен `auth_sessions`; права берутся
из `users.role` на сервере. RPC повторно проверяет роль администратора в транзакции.
RLS включён; anon/authenticated не имеют доступа к таблице или RPC. Сервисный ключ
остаётся только на сервере. Автор не может назначить себе принятие.

Хеш ревизии включает analysis_id, хеши оригинала/PNG, каноническое состояние и
родителя. Повтор логически одинакового запроса возвращает ту же ревизию. RPC
сериализует изменения владельца advisory-lock'ом; уникальные индексы не допускают
два новых корня для одной пары analysis/image и двух детей одного родителя.
При конфликте возвращается 409, черновик сохраняется, у родителя доступна ссылка
на следующую ревизию. Автоматического слияния геометрии нет.

Storage и PostgreSQL не имеют общей транзакции: сначала пишется immutable blob,
потом регистрируется ревизия. Сбой/конфликт может оставить незарегистрированный
blob. Повтор исходного запроса восстанавливает регистрацию, если конфликта нет.
Такие blobs не входят в очередь и экспорт, чтение v2 без метаданных даёт 409.
В старом списке Storage имя такого объекта может оставаться видимым. Автоматическая
очистка orphan-объектов намеренно не выполняется; удалять их можно только отдельной
проверенной процедурой после сверки с DB и незавершёнными запросами.

## Черновики и интерфейс

Из отчёта открывается рабочий экран, из него — существующий редактор. Геометрия
записывается при изменениях, а не только при нажатии «Готово». Оригинал записывается
один раз; снимок JSON записывается через временный файл и rename с flush.
Восстановление доступно через «История → Сохранённые контуры → Черновики на устройстве».
Путь: application-support/contour-drafts-v1/{user_uuid}/. Токены в файлы не пишутся.
Восстанавливается последний успешно записанный снимок; принудительное убийство
процесса во время записи может потерять только ещё не завершённую запись.
Очистка данных приложения удалит локальные черновики. Удаление одного лишь кэша
не должно затрагивать application-support. Шифрования сверх Android app sandbox нет.

UUID владельца сохраняется при штатной авторизации; для существующей установки
он получен через `/auth/me`. Для первого использования после обновления нужен
успешный вход/загрузка профиля; затем локальный черновик можно открыть без сети.
Смена аккаунта скрывает изображения/точки, не применяет запоздалые ответы и
не переназначает существующие черновики новому владельцу.

Сохранённая запись показывает серверный статус и причину решения. В админке
«Проверка контуров» показывает оригинал, PNG, переключаемое наложение, историю,
принятие и отклонение. Принятие маски **не подтверждает** высоту, DBH или механику.

## Совместимость

- Старый клиент: прежний POST/GET `/v4/corrections` работает без новых полей.
- Старые schema_version=1 / pending_review PNG открываются без изменений.
  Редактирование начинается явной кнопкой создания нового контура по фото;
  исходные точки не выдумываются. Запись можно явно отправить на проверку.
- Для включения всех прежних pending_review в очередь предусмотрен явный
  идемпотентный индексатор ниже. Он не меняет blobs и не принимает маски.
- Новый клиент со старым API или без миграции: сообщает, что ревизии и модерация
  недоступны; оставляет локальные точки и предлагает явно сохранить только PNG
  старым POST. Автоматического понижения формата и потери точек нет.
- При недоступной DB новый workflow отвечает 503. Старые PNG остаются читаемыми,
  v2 не выдаёт устаревший статус вместо ошибки. Установка нового клиента до backend
  допустима, но весь цикл станет доступен только после миграции и обновления v4.

## Граница с обучением / контракт экспорта

Обучение **не подключено**: `eligible_for_training` всегда false. Код не пишет
в verified bucket, не устанавливает retrain-флаги и не меняет модель.
Существующий `tools/export_from_supabase.py` читает verified bucket;
`tools/export_yolov8_dataset.py` принимает manifest.selection.train_ids/val_ids,
читает `input.jpg` и `user_mask.png`, проверяет размеры, геометрию, fidelity маски
к YOLO-полигону и точное совпадение SHA256 фото между train/val.

Будущий отдельный адаптер должен:

1. Получить доверенный snapshot metadata DB + private blob, выбрать только
   accepted с неизменяемым решением actor/time; сохранить owner, correction_id,
   parent_id, original analysis_id, image/mask SHA256 и snapshot timestamp.
2. Проверить хеши и декодирование, размер/ориентацию и содержимое PNG; согласовать
   правила polygon fidelity с существующим экспортёром. Принятие геометрии не
   превращать в метку точности физических измерений.
3. Выбрать **одну** принятую ревизию на группу исходного изображения до разделения
   выборки. Группировать по SHA256 байтов и ориентированных пикселей, включая
   разные analysis_id/владельцев. Для повторных фото одного дерева дополнительно
   нужен tree/session grouping; одинаковые пиксели не решают near-duplicate leakage.
4. Зафиксировать split на уровне группы. Разные ревизии одного фото запрещены
   одновременно даже внутри одного split, тем более между train и validation.
5. Создать отдельный versioned staging dataset, связать safe sample_id с revision_id,
   передать явный manifest существующему экспортёру, затем повторить его integrity
   и fidelity проверки. Нельзя просто поменять bucket экспортёра на corrections.

`tools/contour_export_contract.py::validate_selection` — локальный проверяемый
барьер для такого будущего адаптера: принятие и audit, хеши, PNG/размеры, запрет
дубликатов декодированных изображений. Он **не является адаптером**, не скачивает
данные, не создаёт датасет и не запускает обучение. Тесты закрывают попадание
двух ревизий одного фото в train/val. Реальная интеграция экспортёра — следующий этап.

## Развёртывание оператором (после ревью)

Проверьте на staging и сделайте резервную копию DB/bucket по штатной процедуре.
Нужен PostgreSQL UUID `public.users.id`, существующее поле `users.role` и private
bucket. Выполните migration как владелец DB через Supabase SQL Editor или psql.
Не выдавайте RPC/таблицу anon/authenticated. Никакие секреты не передавайте в чат.

На VPS из каталога отдельного checkout этой ветки (путь выберите по своей установке):

```bash
git fetch origin codex/contour-workflow
git switch --detach origin/codex/contour-workflow
# DATABASE_URL задаётся локально оператором безопасным способом, не печатать.
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f deploy-vps/migrations/001_contour_workflow.sql
docker image tag arborscan-api-v4 arborscan-api-v4:before-contour-workflow
docker compose -f deploy-vps/docker-compose.v4.yml build api-v4
docker compose -f deploy-vps/docker-compose.v4.yml up -d --no-deps api-v4
curl --fail https://31.57.170.88/api/v4/health
# Индексатор читает существующие server credentials внутри контейнера, не выводя их.
docker compose -f deploy-vps/docker-compose.v4.yml exec -T api-v4 python -m arborscan_v4.index_legacy_contours
# После проверки количества кандидатов:
docker compose -f deploy-vps/docker-compose.v4.yml exec -T api-v4 python -m arborscan_v4.index_legacy_contours --apply
```

Индексатор по умолчанию только читает; --apply импортирует старые записи в очередь
submitted. Повтор безопасен, принятие существующей записи не сбрасывается. Он
выводит только счётчики, не токены, владельцев или содержимое изображений.
Для нового API Nginx уже сохраняет нужный маршрут `/api/v4/v4/corrections/...`;
изменять конфигурацию TLS или Nginx не требуется. V3 обновлять не нужно.

На Windows:

```powershell
cd D:\arborscan_backend\arborscan_app
flutter pub get
flutter test
flutter analyze
flutter build apk --debug
$adb = "$env:LOCALAPPDATA\Android\Sdk\platform-tools\adb.exe"
& $adb devices -l
& $adb -s DEVICE_ID install -r build/app/outputs/flutter-apk/app-debug.apk
& $adb -s DEVICE_ID shell am start -n com.example.arborscan_app/.MainActivity
```

Проверка после развёртывания: вход автора → новый контур → прервать редактор
принудительной остановкой → восстановить черновик через Историю → закончить и
сохранить → перезапуск → восстановить точки → сохранить новую ревизию → отправить.
Администратор сравнивает фото/PNG/наложение и отклоняет с причиной; автор видит
причину, создаёт следующую ревизию и отправляет; администратор принимает. Ещё одна
правка принятой ревизии должна снова иметь draft и требовать отправки. Проверить
разрыв сети, повтор сохранения, второй клиент с устаревшим parent, другой аккаунт,
старый PNG и старое приложение. Автору доступ к административным endpoint'ам запрещён.

## Откат без удаления данных

Сохраните таблицу и private blobs: их удаление уничтожит ревизии/историю.
Аддитивная миграция не мешает старому API; откат DDL не требуется.

```bash
docker image tag arborscan-api-v4:before-contour-workflow arborscan-api-v4
docker compose -f deploy-vps/docker-compose.v4.yml up -d --no-build --no-deps --force-recreate api-v4
curl --fail https://31.57.170.88/api/v4/health
```

Новый клиент после отката показывает недоступность workflow и сохраняет локальные
черновики; старый API продолжает читать PNG. Если нужен откат APK, соберите
`be8485b` в отдельном checkout и установите через `adb install -r` с тем же ключом
подписи, без uninstall/clear-data. Ревизии/черновики не удаляйте; после возврата
workflow они снова доступны.
