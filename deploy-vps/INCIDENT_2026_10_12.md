## Фактическая причина - первоначальная диагностика

Пользователь сообщил об отказе входа и анализа в установленной сборке
«Лесной атлас». Скриншоты показывают plain-text `Internal Server Error`,
ошибку JSON-парсера и `Contour workflow migration is not ready`.

Read-only проверка агента установила:

- Публичные v3/v4 HTTPS health возвращают 200; штатная TLS-проверка включена.
- API-контейнеры доступны через SSH, запущены 08.10 и показывают healthy.
  Эти health не подтверждают доступность зависимостей.
- Запросы из обоих API к Supabase REST для users и трёх version RPC возвращают
  **HTTP 402**. Журнал v3 указывает `exceed_cached_egress_quota` и
  `exceed_egress_quota`: сервис ограничен провайдером за превышение трафика.
- Активный проект Supabase имеет статус ACTIVE_HEALTHY, организация - **Free**.
  Статус проекта не отменяет billing-ограничение REST API.
- Через подключённый SQL-инструмент проверены фактические функции:
  `contour_workflow_version()`, `server_history_version()`,
  `model_quality_version()` - все вернули **1**. Миграции повторять не требуется.

Образ v3: `sha256:60c6cf1fc185e41aaf6275522df851b60f142887554685ce7aec49b3f702a990`.
Образ v4: `sha256:034a9d67b49adb5565a1af9454706a104721e21160d725db32a31f796ff20193`.
Worker: `sha256:3fe28a5b7eb5716a71e984908520c31fff9ac325a9c5885c5e102e93996ac14a`,
текущий health unhealthy; отдельная причина его health в этом инциденте не установлена.
На этапе первоначальной диагностики образы/контейнеры не заменялись
и не перезапускались. Последующее переключение использует те же API images.

## Трафик прежних облачных резервных копий - первоначальная диагностика

Прочитаны только заголовки локального backup-архива и служебные метаданные.
Новые резервные копии/restore не запускались; содержимое пользовательских файлов
и таблиц не выводилось. SQL-агрегат Storage и последний полный архив согласованы:
2252 объекта, 759394548 байт. Архив также содержит 68773247 байт данных 15 таблиц;
snapshot читает таблицы дважды для проверки изменений.

Ежедневный snapshot заново скачивает все Storage-объекты. Примерная нижняя
оценка только файлов - 0,759 ГБ за полный запуск, около 22,8 ГБ за 30 запусков,
без таблиц, обычного приложения и ручных проверок. Это существенный источник
трафика и не совместимо с бесплатной месячной квотой 5 ГБ. Точная разбивка всего
биллингового расхода и дата следующего цикла через доступные инструменты не получены;
не утверждается, что backup был единственным источником расхода.

На VPS остались 14 каталогов с COMPLETE. Последний служебный success -
`20261010T032353Z` / `daily-2026-10-10`. Marker незавершённой операции -
`daily-2026-10-11`. Systemd timer active/waiting; последняя попытка 12.10
03:20:04-03:31:12 UTC, ExecMainStatus=1/Result=exit-code. Следующий запуск
13.10 03:21:33 UTC. Наличие COMPLETE не выдаётся за новую проверку целостности
всех 14 копий. Таймер, ротация и сами копии не изменены.

## Исправление ошибочной интерпретации - отдельный локальный пакет

- `server.py`: отказ провайдера/сети возвращает безопасный JSON 503; upstream
  body не попадает в ответ. Сбой проверки сессии не превращается в ложную 401.
- `arborscan_v4/correction_workflow.py`: HTTP 402/429/5xx и ошибки транспорта
  отделены от фактически отсутствующих RPC/таблиц. Прежние 409/403/404 сохранены.
- Flutter: статус HTTP проверяется до JSON-декодирования. 500/503 получают
  понятное сообщение о временной недоступности; внутренний текст миграции и
  plain-text/HTML не показываются. Сессия, черновик и фото сохраняются.

Новые проверки: 64 backend-теста + 15 subtests прошли, 38 целевых Flutter-тестов
прошли. `flutter analyze`: 51 прежнее замечание, 0 новых, 0 errors.
`git diff --check` затронутых файлов чистый.
Доказательства: `output/incident-20261012/backend-error-tests.txt` и
`output/incident-20261012/flutter-checks.json`.
Это локальные автоматические проверки; новый APK, установка и UI S24 не выполнены.
ADB в этой среде не видит телефона. Main, production SQL и политика Google не менялись.
Этот отдельный пакет ошибок не включён в сохранённые API images текущего
переключения; восстановление выполнено переносом рабочей зависимости.

## Рассмотренный внешний шаг и границы - исторический вариант

Владельцу передан один запрос выбора: немедленно восстановить доступ через
платный тариф либо сохранить Free и подготовить экономный режим с ожиданием
сброса квоты. Подписка/платёж и Spend Cap агентом не меняются.
Уменьшение будущего расхода не обнуляет уже использованный трафик.

Официальные источники, проверены 12.10.2026:
[Egress](https://supabase.com/docs/guides/platform/manage-your-usage/egress),
[подписка](https://supabase.com/docs/guides/platform/manage-your-subscription),
[Billing](https://supabase.com/dashboard/org/_/billing),
[Usage](https://supabase.com/dashboard/org/_/usage).
По документации ограничение снимается с началом следующего расчётного цикла
либо повышением тарифа; отключение Spend Cap применимо к соответствующему платному
тарифу и не используется как автоматическое решение для текущего Free.

После подтверждённого снятия HTTP 402 необходимо проверить dependency RPC по
штатному REST-пути и настоящий вход/анализ с разрешёнными тестовыми данными.
На этом этапе восстановления приложения ещё не было. Локальное улучшение ошибок
не снимает ограничение провайдера; обход REST/авторизации и подмена результата
анализа не реализованы. Экономная backup-схема требует отдельной проверки
сохранности и restore, прежде чем менять действующее расписание/формат.

## Вариант без новой подписки - исследование до переноса 12.10.2026

Пользователь сообщил, что бюджет на Pro отсутствует. Покупка тарифа не считается
обязательным следующим шагом; подписка и production в этом исследовании не менялись.
Рекомендация агента - подготовить перенос прикладной БД и файлов на уже оплаченный
VPS, используя существующий проверенный AS-14 recovery stack. Это рекомендация,
а не выполненное переключение и не разрешение на миграцию production.

Read-only проверены основания:

- Flutter обращается к нашим HTTPS API v3/v4; для контуров/отчётов фото и маски
  возвращаются через API. Прямая зависимость клиента от Supabase Storage не найдена.
- Вход ArborScan использует собственные `public.users/auth_sessions`, хеши паролей
  и Google subject, а не Supabase Auth/GoTrue.
- В [POSTGRES_RECOVERY.md](POSTGRES_RECOVERY.md) сохранены реальные результаты
  отдельного восстановления PostgreSQL + PostgREST + Storage API/file backend
  и проверки API, отчётов, контуров, прав и перезапуска 28.09. Это исторические
  проверки lab, не новое подтверждение готовности нынешнего production-кандидата.
- VPS: 6 CPU, 11925 МиБ RAM, 10459 МиБ available, 43 ГиБ свободного диска
  на момент проверки. Это запас для подготовки; нагрузка нового стека не измерена.
- Уже установленный приватный PostgreSQL-клиент с `service=arborscan_backup`
  успешно выполнил только `SELECT 1`. Секреты не выведены. Это не новый dump,
  не restore и не обход ограничений REST для работающего приложения.

Перед переносом нужны актуальная копия БД и сверка всех файлов с проверенными
архивами, текущие точные API/worker images, сохранение аккаунтов/сессий/owner ID,
закрытые DB/REST/Storage, production-ключи и их ротация, Google/внешние API,
проверка полного цикла и откат. `ops_recovery_stack.py` нельзя использовать
без изменений: он обезвреживает сессии и задания в тестовой копии, выдаёт
30-дневные lab JWT и содержит старые значения по умолчанию. Production-модели,
решения модерации и исходные файлы при переносе не должны меняться.

Альтернатива - оставаться на Free после сброса квоты и разработать проверенный
кеш для скачивания только новых/изменённых файлов с локальной сборкой полного
архива. Она не снимает текущий HTTP 402 и не гарантирует укладывание в квоту:
трафик БД, pg_dump через Supavisor и обычная работа приложения также учитываются.
Простое сохранение файла по прежнему bucket/path не доказывает неизменность,
поскольку старые загрузки допускают upsert. Windows chunk/delta экономит
VPS-to-PC передачу, но не Supabase-to-VPS.

После собственного переноса дневные копии могут читать локальную БД и файлы
без повторного облачного скачивания. Копия на том же VPS не независима от его
потери; существующая `D:\ArborScanBackups` остаётся вторым местом и зависит от
доступности ПК. На момент исследования новые серверы/платные услуги не заказаны,
DB/Storage и таймер не менялись, восстановление входа/анализа ещё не подтверждалось.
Фактический последующий перенос и оставшиеся эксплуатационные проверки записаны
в начале этого документа.
