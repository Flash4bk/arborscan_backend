# AS-14 / AS-16: условия проверки переноса

Этот файл описывает проверку и ограничения, а не объявляет переключение
production выполненным. Фактические результаты и выбранный root фиксируются
в основном отчёте переноса. Основной план сохраняет остальные этапы проекта.

## Контроль до тестовых записей

`ops_selfhost_audit.py` сопоставляет исходные и восстановленные отпечатки всех
строк public-таблиц, включая `users`, хеши паролей, `auth_sessions`, владельцев,
родителей ревизий, решения модерации и задания моделей. SQL выполняется в
`REPEATABLE READ READ ONLY`; отпечатки не содержат строк пользователей.
Версии трёх модулей должны быть 1/1/1, отсутствующие владельцы недопустимы.

Для обоих PostgreSQL используют **одинаковые** SQL-файлы
`selfhost_fingerprints.sql` и `selfhost_storage_fingerprints.sql`. Они явно
задают UTC, ISO, `extra_float_digits=1` и сортировку JSON по `COLLATE "C"`.
Различие настроек сериализации или сортировки нельзя объявлять потерей данных
без сравнения, но нельзя и игнорировать несовпадающий отпечаток. После изменения
канонизации снимают новые исходные отпечатки, сохраняя прежние результаты.

Полные отпечатки `storage.objects` и `storage.buckets` включают все колонки:
идентификаторы, владельцев, версии, даты, MIME/размеры и прочие метаданные.
Они проверяются после посева физических файлов, **до** HTTP-чтений и создания
DEMO-записей. Импорт файлов не должен делать Storage API upsert, заменяющий
версии и владельцев в восстановленной базе.

Сохранённые байты сверяются с SHA256 проверенной архивной копии. Когда облачный
Storage не позволяет прочитать файлы заново, такая сверка сама по себе не
является независимой свежей выгрузкой каждого облачного файла. Дополнительно
сверяют актуальный полный набор ключей, размеры и признаки изменений с датой
копии; возраст копии и отсутствие свежей проверки байтов указывают в отчёте.

Проверка читает каждый локальный объект потоково и сопоставляет SHA256/размер.
Для всех индексированных отчётов и контуров дополнительно открывает реальные
оригиналы и PNG-маски, проверяет связанного владельца, хеши и размеры с учётом
EXIF. Использует внутренний service key, не создавая сессии реальных владельцев.
Это проверка файлов и индексов, а не доказательство интерфейсного сценария S24.

Запущенные контейнеры проверяются через Docker inspect: точные образы,
эффективное окружение, принадлежность нужному проекту и loopback-порты.
Защищённые Google-переключатели и выбор моделей сравниваются по хешам; модели
сверяются по SHA256. Экранирование Compose `$$` снимается ровно один раз;
подстановка переменных оболочки или интерпретация `${...}` не выполняется.

Gateway обслуживает только внутренние REST/Storage-запросы. Проверки HTTP API
используют отдельные loopback-порты v3/v4 из Compose; внешние `/api/v3` и
`/api/v4` снимаются ровно один раз. TLS публичного nginx не отключается.

## Старые адреса и интерфейс

Аудитор считает абсолютные ссылки по категориям, отдельно проверяя
`users.avatar_url` и сохранённые JSON отчётов/контуров. URL, объектные ключи,
аккаунты и токены в публичные доказательства не выводятся.

Действующий `ApiConfig.imageUrl` оставляет абсолютные адреса неизменными.
В текущем Flutter сетевое изображение используется для аватара профиля;
изображения отчётов и контуров читаются из base64. Наличие старой Supabase-ссылки
в записи не означает, что действующий экран обращается к ней; это проверяют
по вызывающему коду. Старый облачный аватар всё же может стать недоступным.
Безусловная замена ссылок внутри сохранённых пользовательских отчётов не входит
в процедуру переноса. Отдельная проверка установленного приложения необходима
для подтверждения его поведения.

## DEMO и перезапуск

После сравнения исходных данных `--smoke` создаёт два новых аккаунта
`DEMO-selfhost-recovery` с случайными паролями. Только второй новый аккаунт
получает роль администратора в проверяемой копии. Проверяются обычный вход,
отказ без токена, изоляция владельцев, две версии отчёта, повтор одинакового
сохранения, старый PNG, отклонение с причиной, принятие и новая неподтверждённая
правка. Обучение не запускается, реальная очередь модерации не меняется.

Файл `fixture.private.json` имеет права 600 внутри каталога 700. После
согласованного перезапуска `--repeat-smoke` проверяет вход и чтение именно
созданных записей. Он не сравнивает исходные общие количества после собственных
записей. Незавершённый fixture сохраняется для разбора и не выдаётся за успешно
проверенный перезапуск. Удаление реальных записей или скрытая очистка в `finally`
не выполняются.

Worker в этом восстановительном тесте остановлен. Нельзя объявлять проверку
работающего worker или готовность обучения, используя только сохранённый образ
и конфигурацию. Причина и ограничения должны остаться в отчёте.

## Переключение и откат

До переключения сохраняют private Docker inspect всех прежних контейнеров,
точные образы, конфигурацию, runtime и свежую проверенную копию новой базы и
файлов. Модели, applicationId, подпись, HTTPS и внешние маршруты сохраняются.

Остановка и переименование прежних контейнеров сохраняют их для разбора, но
не меняют старые Compose labels и restart policy. Политика `always` может
возобновить старый контейнер после перезапуска Docker и занять нужный порт.
Такие rollback-контейнеры должны оставаться остановленными; фактическое
изменение restart policy фиксируют отдельно после снимка исходного состояния.
Старый `docker compose up` нельзя использовать как команду обслуживания нового
production. Команды указывают точный новый Compose-файл.

До новых пользовательских записей возможен возврат к прежним контейнерам,
но прежний облачный API может по-прежнему отвечать 402. Это не восстановление
доступности. После новых записей запуск прежнего контейнера с его прежним
`SUPABASE_URL` скроет новые данные и недопустим как незаметный откат.

Предпочтительный откат приложения после новых записей сохраняет новую БД,
Storage и актуальные write-volumes: контейнер пересоздают из сохранённого
проверенного образа, сохранив локальные реквизиты зависимости. Окружение
существующего Docker-контейнера нельзя заменить его простым переименованием.
Возврат всей БД требует отдельного окна обслуживания, свежей копии и явного
учёта записей после переключения; старая копия не заменяет новые данные молча.

Ежедневная процедура backup должна читать уже локальную БД и локальные файлы,
а не продолжать полную загрузку из ограниченного Supabase. Новую процедуру,
целостность набора и восстановление проверяют до объявления эксплуатации
готовой. Контейнеры БД/REST/Storage не публикуют внешних портов; gateway и
application API слушают только `127.0.0.1` за действующим HTTPS nginx.
