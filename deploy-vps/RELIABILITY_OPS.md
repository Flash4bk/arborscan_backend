# AS-14: надёжность и эксплуатация, 26.09.2026

Ветка `codex/reliability-ops`, основа `63405e5` (AS-12). Выполнена агентская
проверка перечисленного ниже. AS-14 **не закрыт полностью**: нет проверенного

## Исправления

| Приоритет / дефект | Исправление | Доказательство |
|---|---|---|
| P1: правка заменяла неподтверждённый version_id после потери ответа | До отправки записывается upload_attempted, прежняя версия сохраняется до повторного подтверждения; операции сервиса сериализованы | Потеря ответа после имитации commit, пересоздание сервиса, повтор с одним ID/одной записью, блокирование замены |

| P2: mutable photo могла измениться до записи в очередь | Копия байтов при постановке записи; другой оригинал в прежнем localId отклоняется | Файл после пересоздания содержит исходные байты |
| P2: 5xx показывал «не сохранён» | Пишется «операция не подтверждена»; 403 не превращается в 401 | Тесты кодов и потерянного ответа |

| P1: тяжёлые запросы не ограничивались до multipart | Максимум 2 изменяющих запроса на процесс, остальные 429/Retry-After; 40 MiB body, 30 сек ожидания очередного chunk | ASGI тесты переполнения, chunked запроса, освобождения слота после исключения |
| P2: worker heartbeat обновлялся без рабочей БД | Heartbeat после успешного RPC; отдельная проверка версии схемы | Тест отказа БД не создаёт heartbeat |
| P1: SIGTERM worker мог оставить дочерний процесс | Завершение process group и durable failed при прерывании; при недоступной БД остаётся прежний механизм lease expiry | Тест SystemExit, lost lease, cancel, exit code, лимит диска |

Новых очередей, автоматических бесконечных повторов и изменений алгоритмов измерения
нет. После неопределённого сохранения пользователь повторяет прежнюю операцию из истории;
API возвращает ту же immutable версию. Если предыдущая операция не подтверждена, новую
правку этого localId сохранить нельзя до разрешения результата. Это сознательное ограничение,
а не автоматическое слияние. Решения модерации и отчёты сохраняют разные контракты.

## Ресурсы и диагностика

VPS: RAM ~11.9 GiB, до работ свободно ~126 GiB диска. Worker: существующие лимиты
2 CPU / 3 GiB без дополнительного swap, минимум 5 GiB свободного диска, один child.
API принимает до 15 MiB оригинала, маску до 8 MiB, декодированное изображение до
25 млн пикселей. Новый общий лимит multipart 40 MiB оставляет запас под метаданные;
не более двух изменяющих запросов на процесс ограничивают одновременные аллокации.
Это не доказательство отсутствия OOM при произвольной нагрузке/числе процессов.

API json-file: 5×10 MiB, worker: 3×10 MiB — существующая ротация сохранена.
Новый x-request-id генерируется сервером; журналирует ID, статус и длительность,
без тела/токенов/пользователя/URL. HTTP health показывает загрузку модели, не всю
готовность зависимостей. Отдельная команда проверяет схемы и private bucket:

```sh
python3 /home/arborscan/ops-tools/ops_status.py
docker logs --since 10m arborscan-api-v4 2>&1 | grep -E 'request=|ERROR|Traceback'
```

Наличие heartbeat не доказывает качество обучения. Отказ базы делает его просроченным;
lease остаётся источником прав на job. Стресс, заполнение диска и отключение сети
проверялись только через изолированные тестовые зависимости, не на пользователях.

## Карта хранения и реальная копия

- Supabase public tables: пользователи/сессии, analyses, contour_revisions,
  report_versions, ml_taxon_labels/snapshots/jobs/models/active_models и прочие
  таблицы, доступные текущему service-role через PostgREST.
- Storage: девять фактически найденных buckets — inputs, predictions, meta,
  arborscan-models, raw, verified, models, datasets, corrections. Их имена с полными
  префиксами зафиксированы в приватном snapshot manifest. Объекты выгружены отдельно
  от таблиц: стандартная копия БД не включает Storage bytes.
- `/opt/arborscan/models`: ~93 MiB; `/home/arborscan/model-quality`: worker/registry
  runtime. Конфигурация compose, приватный env и Docker inspect копируются с mode 600.
- Локальные черновики телефонов не попадают в серверную копию; очистка приложения или
  потеря телефона уничтожает неотправленные данные. Они не являются межустройственной синхронизацией.

Успешная копия: `/home/arborscan/ops-backups/20260926T202023Z`, marker COMPLETE.
Проверены SHA256SUMS. Application tar ~792 MiB; локальные файлы ~93 MiB.
Дополнительно старые Docker images сохранены в
`/home/arborscan/reliability-backup-20260926/runtime.tar` (~581 MiB), checksum проверен.
Первая попытка application.partial.tar оборвалась по SSH, не объявлена завершённой
и не удалялась. Успешная повторная копия находится в другом каталоге.

`ops_snapshot.py` читает все доступные tables и objects, отмечает версии схем,
проверяет неизменность таблиц повторным чтением, публикует manifest только в конце.
`ops_backup.sh` использует flock, .partial, timeout 30 минут, минимум 20 GiB,
не удаляет старые копии; после 14 COMPLETE останавливается до архивирования оператором.
Это **прикладной снимок, не транзакционный PostgreSQL backup**: SQL functions/RLS/roles/
triggers и внутренние схемы не восстанавливаются из OpenAPI. Возможны конкурентные
изменения Storage и живых таблиц, поэтому полноценный pg_dump/PITR остаётся необходимым.

Официальная граница охвата: [Supabase Database Backups](https://supabase.com/docs/guides/platform/backups).
Наличие тарифа/автоматических копий Supabase не проверено и не утверждается.
Прямого PostgreSQL-доступа в использованной среде нет. Для полного restore нужен
приватно настроенный DSN/pg_service и отдельная тестовая база без production прав;
пароли в чат передавать не нужно. Подготовленный операторский путь:

```sh
pg_dump 'service=arborscan_backup' --format=custom --file=arborscan-db.dump
pg_restore --dbname='service=arborscan_restore_test' --no-owner --no-acl arborscan-db.dump
```

Это **не выполнено**; параметры service должен задать оператор в защищённом pg_service.conf,
а проверку RLS/ролей проводить отдельно, поскольку --no-acl их не восстанавливает.
Копия остаётся на том же VPS, не защищает от его потери. Off-site место не подключено.

## Расписание

Разовая копия выполнена. Cron отсутствует, sudo требует интерактивного подтверждения,
user systemd имеет Linger=no. Подготовлены и проверены `systemd-analyze verify` файлы
`arborscan-backup.service/.timer`: ежедневно 03:17 UTC, случайная задержка до 5 минут.
**Включение не подтверждено**; пользователю передана одна команда установки с sudo,
существующие unit-файлы она не перезаписывает. После выполнения проверить:

```sh
systemctl list-timers arborscan-backup.timer
systemctl status arborscan-backup.service --no-pager
python3 /home/arborscan/ops-tools/ops_status.py
```
