# Runtime: фиксированный кандидат и отдельная чистая сборка

AS-01, AS-14, AS-16 / REL-01. Проверено локально 12.11.2026.
Production не изменялся. Docker на этом Windows-ПК отсутствует, поэтому
новые Linux-образы не собирались и не запускались.

## Что зафиксировано

`runtime-lock.json` содержит точные ID двух наблюдавшихся образов и полный
список имён/версий установленных Python-пакетов. Данные прочитаны через
`importlib.metadata`, без env, строк подключения, исходных URL пакетов и
импорта ML-моделей. v3: Python 3.11.16, 100 дистрибутивов; v4: Python
3.11.16, 59. Это снимок метаданных, не проверка известных уязвимостей.

Образы:

- v3: `sha256:60c6cf1fc185e41aaf6275522df851b60f142887554685ce7aec49b3f702a990`.
- v4: `sha256:2abb56ed5d84e4ddbe4465da851c842861498101f030fab016f66630c4ee1762`.

Оба старых runtime содержат два дистрибутива, предоставляющих `cv2`:
`opencv-python` 5.0.0.93 и `opencv-python-headless` 4.10.0.84. Наличие
метаданных не доказывает, какой native-файл реально используется. Их
удаление из работающего контейнера или скрытое обновление запрещены.
Кандидат overlay сохраняет прежние пакеты и слои. Будущая чистая сборка
декларирует только `opencv-python`, который требуется Ultralytics.

## Overlay из точного коммита

Предпочтительный следующий путь для исправления кода - существующий
runtime без сетевого разрешения зависимостей. Сначала завершить и
проверить исходный коммит в рабочей ветке. Подготовить два новых каталога:

```powershell
$releaseCommit = (git rev-parse HEAD).Trim()
python deploy-vps/runtime_candidate.py --role v3 --revision $releaseCommit --output output/runtime-v3-candidate
python deploy-vps/runtime_candidate.py --role v4 --revision $releaseCommit --output output/runtime-v4-candidate
```

Команда читает Git-объекты указанного полного SHA, а не изменяемые файлы
рабочего дерева. Неполный коммит, отсутствие новых модулей и повторное
использование каталога отклоняются. В контекст попадают только явно
разрешённые Python-файлы. Env, модели, отчёты и данные не копируются.
`provenance.json` сохраняет исходный SHA, ID базы и SHA каждого файла;
поле `built` остаётся false до реальной успешной проверки образа.

На отдельном разрешённом Linux/Docker-узле с теми же исходными коммитом
и сохранёнными базовыми образами команды выполняются с новым каталогом
и дополнительным `--build`. Это локальная сборка, не развёртывание:

```bash
release_commit=$(git rev-parse HEAD)
python3 deploy-vps/runtime_candidate.py --role v4 --revision "$release_commit" --output output/runtime-v4-checked --build
```

Перед сборкой инструмент проверяет точный локальный image ID. Docker
собирает с `--network=none --pull=false`, без pip/apt. Отдельный контейнер
запускается без сети, с read-only root и временным `/tmp`: сравнивает
Python/весь набор пакетов, импортирует cv2/NumPy/Torch/Torchvision,
Ultralytics и адаптеры, проверяет CPU Torch. Только затем фиксируется
ID кандидата. API-процесс не запускается, production-контейнеры не заменяются.
До обращения к Docker проверяются SHA файлов подготовленного контекста,
точный Dockerfile и отсутствие лишних файлов/ссылок. После сборки внутри
кандидата повторно проверяются исходные SHA и отсутствие старых Python-модулей
в заменяемых пакетах. Изменённый после подготовки контекст отклоняется.
Обычные интеграционные тесты API/хранилища и smoke реального кандидата
должны пройти отдельно; import-проверка их не заменяет.

Старый `Dockerfile.v4-contour` также получил COPY/whitelist для
`arborscan_science`. Сам по себе он принимает произвольный BASE_IMAGE;
для проверяемого выпуска использовать инструмент выше.

## Чистая сборка - отдельный непроверенный кандидат

`requirements.runtime-v3.lock.txt` и `requirements.runtime-v4.lock.txt`
закрепляют все наблюдавшиеся версии, кроме второго провайдера cv2.
Это наборы версий для Linux x86_64 / Python 3.11, не lock с SHA колёс.
Они не устанавливались в production и не называются подтверждёнными
чистыми окружениями. Локальный audit-venv имеет другие версии; его тесты
не подтверждают ABI будущего образа.

Production Dockerfile и Dockerfile.v4 не имеют плавающей Python-базы:
нужен явный `PYTHON_BASE_IMAGE` вида
`python:3.11.16-slim-bookworm@sha256:<проверенный manifest digest>`.
Этот registry digest не равен image config ID из снимка выше. Сначала
нужно независимо получить и проверить нужный digest; здесь он не выдуман.
v3 дополнительно требует `COCO_MODEL_SHA256` существующего разрешённого
`yolov8n.pt`: скачанный файл проверяется по нему до успешной сборки.

Оба Dockerfile закрепляют build tools и CPU Torch, устанавливают полные
версии с `--no-deps`, выполняют `pip check` и native-import gate. Ошибка
разрешения версий, несовместимость Torch/Torchvision, отсутствие нужного
колеса или конфликт OpenCV останавливают сборку. Автоматического возврата
к `latest`, CUDA либо второй версии OpenCV нет.

Открытые проверки для чистого образа: доступность и SHA всех wheels,
закреплённая ОС/apt snapshot, реальная Linux-сборка, native ABI, API/model
smoke и повтор backend-тестов в этом образе. Требуется отдельное решение
об обновлении runtime; наличие файлов версий не закрывает эти проверки.
Старый корневой Dockerfile Railway не является выбранным VPS-путём выпуска.

## Доказательства и откат

`tests_v4/test_runtime_release_contract.py` проверяет отказ от плавающей
базы, неполных исходников, изменённого runtime и опасного каталога;
отдельные временные Git-репозитории доказывают чтение именно коммита и
исключение env. Это локальные тесты инструмента, не запуск Docker.

Для будущего разрешённого обновления сохранять старые ID, архивы образов,
конфигурацию и проверенную копию данных. Overlay не меняет схему/данные
и не заменяет модели. Откат приложения - прежний образ с прежними
параметрами контейнера; изменение production и команда его замены в
текущий локальный этап не входят. Исправленные серверные права после
отката старого v3 снова будут отсутствовать - откат не делает старую
версию безопасной.
