## 1. Добавить явный тест полного сохранения нового научного результата

Раздел11 правильно требует новый версионный `science_result`, серверный result_id,
owner/revision binding и сохранение старого v4 как недоступного. Это реалистичный путь.
Одна замена `beta=null` на переданный клиентом β была бы ошибочной; план такого не предлагает.

По текущему коду изменения необходимы минимум на трёх независимых участках:

- `arborscan_v4/report_history.py:90` принудительно заменяет beta и beta_kg_s на null;
  `validate_snapshot` допускает snapshot version1, `/capabilities` сообщает history_version1.
- `measurement_results_summary.dart:174` и следующие метрики имеют текст недоступности;
  reference-ветвь `server_report_page.dart:208` отдельно пишет «β не рассчитан».
- `report_export_data.dart:360` обрабатывает старое значение β как «Прежнее значение»
  и читает прежние ключи, тогда как новый контракт должен показывать серверно подтверждённую
  научную метрику, её метод и интервал. Наличие поля в JSON само не создаст новый PDF.

Рекомендуемый конкретный gate П02/П10:

```text
server result → mobile display → save report → server reload
→ cached/offline reload → selected-version PDF
```

Один и тот же проверенный ненулевой β, его экспериментальный/предсказанный метод,
интервал и result SHA должны пройти весь маршрут без обнуления/переклассификации
в legacy. Отдельные отрицательные случаи: чужой result_id, другая ревизия/фотография,
поддельное клиентское число, неизвестная schema/capability и смена аккаунта.
Старый контракт должен продолжать честный null; старые snapshots не переписываются.
Такой gate делает общее требование «UI/API/PDF показывают одно» проверяемым именно
на существующих барьерах, а не только на новом лабораторном экране.

## 2. Уточнить область идемпотентности и приватность производных данных

План корректно предусматривает владельца, private history, отдельные права scientific jobs,
RLS и серверные ключи. Для реализации полезно явно определить:

- idempotency key имеет область **owner_id + тип операции**, затем привязку к input hash;
  совпадающий пользовательский ключ другого владельца не возвращает чужое задание;
- те же owner/revision checks действуют для чтения, отмены, повторного запуска,
  артефактов/подписанных ссылок и PDF; привилегированный worker не принимает владельца
  как доверенное утверждение из клиентского JSON;
- общедоступный кеш provider/model/cell можно делить между пользователями, а экспериментальные
  видео, точная привязка дерева, input/result snapshots и локальный offline-кеш остаются
  приватными; смена аккаунта не переиспользует приватный кеш другого владельца.

Это детализация тестов раздела11/П10/П12. В плане уже нет обещания, что одно включение RLS
обеспечит все права автоматически; замечание про отдельные Data API grants сохранено корректно.
